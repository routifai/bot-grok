Findings + implementation plan · Omnigent · 2026-09-29

Context assembly on Omnigent, for Pi, Codex and Claude SDK

A long-lived main session whose prompt is built by a context assembler every time it wakes up, delegating work to task sessions or lighter options. Three harnesses: pi, codex, claude-sdk. The user picks one, or we pick it. Every code reference points into engine/omnigent/omnigent/.

Session: an Omnigent session. The main session talks to the user and lives for months; task sessions do bounded work and live for minutes. Prompt: what a model receives. The user's prompt is what they type; the assembled prompt is what the assembler builds for the main session on each wake-up (the user's prompt, a finished task, or a timer). Record: everything Omnigent stores for a session. Task list: the durable table of delegated work.

Design 1

Who knows what

main session

Knows only the assembled prompt

  • Plus its own base prompt and tool definitions
  • History: the record from the latest summary
  • Harness discarded or revalidated every wake-up
  • Vendor memory off
  • Emits replies and spawn_task calls
task session

Starts from a brief, then works natively

  • Brief + context pack (earlier decisions, dependent reports)
  • Harness keeps and compacts its own history for minutes
  • Vendor memory off
  • Ends with one finish_task report (~1,500 tokens), files by reference
Design 2

The assembled prompt, and why the record can grow forever

Prefixstable
rulestool contractdelegation policyskills catalogcore memory vN
Middleappend-only
summary (compaction item)items since ittask events + reports
Tailper wake-up
open tasks recaprecalled memorytriggertime

Prefix and tail go through the deployment-context hook. The middle is the runner's normal history input. A background summarizer writes our summary as an Omnigent compaction item once 100 items are unsummarized, folding the oldest 50 and advancing a cursor only if no other job moved it. The runner loads from that item and drops its cache, so the input stays bounded while the record keeps every item.

Design 3

Fresh every wake-up, or warm while still valid

pi

A system-prompt change restarts the process, so to stay warm the tail must travel in the turn input as a tagged transient block, not in the system prompt.

codex

Takes new instructions every turn while warm, so the tail can stay in instructions. The easiest of the three.

claude-sdk

Instructions are frozen per client, so the tail goes in the turn input like Pi. It gets the most from staying warm, because a fresh start costs a process.

Phase 4

Rungs 3–6 all write one task list row, end with one finish_task-shaped report, and (asynchronous rungs) one wake-up event. Caps: spawn_bounds 5 per wake-up, ≤ 4 running per main session, depth 1, ≤ 2 retries, USD and time budget per task.

Design 5

The user picks the harness, or we do

User picks

Per main session, stored as harness_override and changed with switch-agent. Switching is safe: the next wake-up rebuilds from the record, and the conversation carries over.

We pick

  • Main session default: pi, the cheapest fresh start with per-turn instructions.
  • codex when recent work is mostly code in a repo.
  • claude-sdk for long writing or document work, or a stated Claude preference; run warm-while-valid.
  • Task sessions choose per task: codex for code changes, claude-sdk for long documents and complex edits, pi for research and light tools.

Implementation plan

Nine phases, each shippable, each with a test

0spike · 2–3 days
  • Does one executor instance serve several sessions (_ensure_executor)? Does close_session of one affect another?
  • Does closing after every turn drop steering messages queued mid-turn?
  • Exact codex _build_initial_prompt replay format.
  • Can the runner send a transient tail block that isn't persisted as the user's text?
  • Can claude-sdk resume from a transcript built from items (reuse harnesses/claude_native/main.py _ensure_local_claude_resume_transcript)?

Accept: a written answer with file:line for each.

1assembler
  • Plug the assembler into OMNIGENT_CONTEXT_PROVIDER; provide() returns prefix and tail with stable ordering, byte budgets, untrusted-data framing.

Accept: on all three harnesses a wake-up's model input contains the assembler's prefix and tail.

2fresh + memory off
  • Label omnigent.fresh_prompt; the adapter calls close_session after each completed turn on labelled sessions.
  • Bundles: context_files: false, skills_filter: "none", codex home without the global AGENTS.md.

Accept: per harness, a fact changed only in the prefix between wake-ups is answered with the new value; a planted host CLAUDE.md/AGENTS.md never appears.

3bounded history
  • Summarizer as a scheduled task: fold 50 at 100 unsummarized, compare-and-set cursor, write a compaction item; the runner drops _session_histories[conv]. Omnigent compaction off for labelled sessions.

Accept: a synthetic 3,000-item session keeps harness input under a fixed budget; the record still returns every item.

4task list · rungs 5–6
  • Task list store; spawn_task (goal, deliverable, harness, depends_on, budget, scope) over sys_session_create/sys_session_send; finish_task; open_result; fallback summarizer; server-side wake; caps.

Accept: fan-out of two, a dependent chain, a failing task with capped retries, a blocked task whose question reaches the user and resumes the same task session.

5harness choice
  • Pick pi/codex/claude-sdk per main session; the auto policy; switch-agent between wake-ups.

Accept: switching mid-life keeps the conversation and holds quality on the eval set.

6warm-while-valid
  • Prefix digest + compaction marker check; keep warm when valid; tail as a transient block for pi/claude-sdk, in instructions for codex.

Accept: claude-sdk median wake-up latency drops with identical answers; prompt-cache hit rate reported.

7structured fresh starts
  • pi: a pi-sdk executor on pi-agent-core taking structured messages, or a Pi session file. claude-sdk: resume transcript built from items. codex: structured replay if Phase 0 found text.

Accept: a tool result from three wake-ups ago is still usable after a fresh start.

8helper · rung 3
  • run_helper on each executor: nested loop with a clean prompt, ≤ 4 in parallel, capped result.

Accept: a research fan-out completes in one wake-up with no new sessions created.

Evaluation, from Phase 2 on

Fixed sessions: question answering, one task, fan-out, dependent chain, failing task, a 200-wake-up session. Measured: tokens per wake-up, prompt-cache hit rate, latency, cost, answer quality against a single-harness baseline, and how often each rung is used (over-delegation check).

Risks

What could go wrong, and the answer to each

Reports are the ceiling

The main session only knows what reports say. Required confidence and open_question, files by reference, and open_result to check.

Flattened fresh starts

pi and claude-sdk lose tool-call structure on a rebuild until Phase 7. Keep summaries tight and tool results referenced.

claude-sdk start cost

A Claude Code process per fresh wake-up. Phase 6 keeps it warm while valid.

Over-delegation

Published multi-agent systems cost about 15× the tokens of chat. The ladder and the eval keep delegation honest.
