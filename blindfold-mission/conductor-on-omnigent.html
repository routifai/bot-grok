System design · side study · independent of Nova

Conductor: one main session, many short task sessions, on Omnigent.

A long-lived main session talks to you and either answers or hands work to task sessions; you only ever see its synthesis. Omnigent stays the core (harnesses, runners, sandboxes, policies, streaming). A context assembler decides what the main session knows each wake-up. This is the design, built from what Omnigent's code already offers, how rakazo's main branch assembles context, and what Anthropic, Manus, Cognition, Letta and others learned running these systems.

two words only

Session: an Omnigent session. The main session talks to you and lives for months; task sessions do the work and live for minutes.

Prompt: what a model receives. Your prompt is what you type; the assembled prompt is what the context assembler builds for the main session each time it wakes up (after your prompt, a finished task, or a timer).

Thesis

Split context ownership by lifetime

main session

Long-lived, assembled

Lives for months. Its context can't be left to a harness that holds a growing session. The assembler owns it: rebuilt every wake-up from durable state, ordered for the prompt cache, small on purpose.

Why: quality degrades with length long before the limit (Chroma, context rot); rakazo already rebuilds a fresh Pi Agent per run.

task

Short-lived, native

Lives for minutes. Bounded work is where a native harness shines, so the harness owns its context (its own compaction, tools and files). The task gets a precise brief and returns one structured report.

Why: in Anthropic's system, workers spend tens of thousands of tokens but return 1–2K (Anthropic); Claude Code subagents return only their final message.

durable state

Outside every prompt

The truth lives in tables: a task list, session history with a compaction cursor, memory. Prompts are views of it. Crashes, restarts and engine switches can't lose anything.

Why: file system and memory tiers as real context (Manus, Letta); durable execution separates reliability from reasoning.

Architecture

Four parts, one database

The main session's assembled prompt

Three zones, ordered for the cache

Every main-session wake-up is assembled fresh into three zones. The order is what makes rebuilding every wake-up affordable. rakazo already orders "stable blocks first, volatile ones last, so the prefix stays cacheable" (run-prompt.ts:20), and Manus calls cache hit rate "the single most important metric" (cached input is 10× cheaper).

Why task reports go in the middle, not the tail

A finished task's report is an event: it happened once and never changes. Appending it keeps the middle append-only, so the whole history stays in cache (Manus: "append-only context, deterministic serialization"). Only live state (which tasks are still open) belongs in the tail.

Why recite the task list at the end

Manus rewrites a todo.md every step to "push the global plan into recent attention" against lost-in-the-middle drift over ~50 tool calls. The tail's short task list digest does the same for a main session juggling many tasks: always last, always current.

Compaction cursor, borrowed from rakazo

When the middle passes a threshold (rakazo: 100 uncompacted messages, compact the oldest 50, summary ≤ 20K chars), the maintenance agent folds the oldest items into the rolling summary and advances the cursor atomically: it only moves if no other worker moved it first. The prefix cache survives; only the middle's start shifts, once in a while.

Keep failures visible

Failed task reports and tool errors stay in the middle instead of being cleaned up. Manus: "keep errors in"; they're the evidence the model needs not to repeat a mistake. The task list stores the attempt count so retries are visible too.

Tasks

A brief in, a report out, nothing else crosses

spawn_task

The brief

Anthropic found vague briefs caused duplicated, misaligned work; each worker needs "an objective, an output format, guidance on tools and sources, and clear task boundaries". So the main session's tool requires them:

spawn_task({
  goal:        "Compare 3 no-FX-fee cards for a Canada→EU traveller",
  deliverable: "table: fee, FX, lounge; ≤ 300 words; sources",
  engine:      "pi" | "codex" | "claude-sdk" | …,
  inputs:      [artifact refs, task list task ids],
  depends_on:  ["T11"],        # wait for, and receive, its report
  budget:      { usd: 0.50, minutes: 10 },
  scope:       "read-only" | "workspace" | …
})

The assembler adds a context pack: the reports of the tasks it depends on plus decisions already made in the main session. That answers Cognition's warning: workers without shared decisions make conflicting assumptions.

finish_task

The report

Every task agent gets one mandatory tool:

finish_task({
  status:    "done" | "partial" | "blocked" | "failed",
  summary:   "≤ 1,500 tokens: findings, decisions made",
  artifacts: [{ ref, kind, title }],   # files stay in the store
  open_question?: "…",                  # becomes an ask to the user
  confidence: 0.0–1.0
})

Artifacts are references, never inlined. The main session can call open_result(task, ref, range) when it truly needs a file (Manus: "compression must be restorable"; Anthropic: just-in-time retrieval). If a task ends without calling it, a cheap model summarizes the child transcript into the same shape.

The missing primitive

The task list

Omnigent has everything else, but not this. Its session_todos is a per-session display snapshot (max 100 items, native/session_todos.py), and the polly example keeps its task registry in a JSON file the agent edits itself (examples/polly/config.yaml:207). A main session that lives for months needs a real table:

tasks
  task_id        pk          session_id     → main session
  parent_task    nullable    child_session → Omnigent child conversation
  goal, deliverable, scope, engine, budget_usd, budget_min
  depends_on     task_id[]   context_pack  jsonb (refs, not copies)
  status         queued|running|done|partial|blocked|failed|cancelled
  attempts       int         lease_owner, lease_expires_at   # rakazo-style leases
  report_summary text        artifacts     jsonb[] (refs)
  open_question  text        confidence    real
  usage          jsonb       # copied from the child's session_usage
  created_at, started_at, finished_at

session_state
  session_id pk · summary text · compacted_up_to_seq · generation   # compaction cursor, compare-and-set
  memory_version · task list_digest_cache

The server writes the task list, never the model directly: spawn_task, finish_task and session-status changes are the only writers. The UI reads it for a live "work in progress" panel.

In one sentence: the assembler fully controls the main session's prompt on every wake-up, and controls only what goes into and out of task sessions. This is the same split rakazo main uses. Every run builds a fresh Pi Agent from host-assembled history (pi-runtime.ts:303), while its nested helpers start from an empty history plus a task string and return only their final text, capped at 12,000 characters (pi-runtime.ts:1132–1254).

How Omnigent talks to harnesses today

The harness holds the history while it's warm

Omnigent is a meta-harness: one server and one database, many agent loops underneath. Reading the executors shows how context actually flows today, and why the main session needs the fresh-prompt mode:

Warm: the harness owns the history

Almost every harness keeps a live session and receives only your newest prompt each time: the Pi RPC process (pi --mode rpc --no-session, inner/pi_executor.py), the resident ClaudeSDKClient (_get_or_create_client), the Codex thread, the OpenAI Agents SDK Session. Each compacts in its own way.

Cold: Omnigent's database is replayed

Omnigent's database stores every session's items (messages, tool calls, reasoning, compaction markers), labels, usage and state. It is replayed into a harness only on a cold start: a new runner, a restart, an engine switch, a reset thread. For Pi and the Claude SDK that replay is flattened to text ("Conversation so far:"), losing the structure of tool calls and images.

Instructions: the real difference

InstructionDelivery in harness_capabilities.py says whether a harness can take new instructions every time: composed-per-turn (pi, codex, openai-agents, copilot, antigravity), composed-session-snapshot (claude-sdk: frozen until the client is rebuilt), first-user-prefix (hermes, cursor, acp, goose, qwen), agent-startup-additive or not-delivered (native CLIs).

Two surprises in the code

Pi restarts when the system prompt changes (_ensure_rpc), so a timestamp in the prompt restarts Pi on every run and replays the history as text. The Claude SDK loads CLAUDE.md unless setting_sources=[], and never sees updated instructions after its first run.

cut

Vendor memory

setting_sources: [] for the Claude SDK, context_files: false for Pi, no global AGENTS.md symlink for Codex. These are memories the assembler can't see or scope, loaded from whichever machine runs the runner.

cut (main session)

Harness-held history

The main session gets a fresh harness every wake-up, with history chosen by the assembler and replayed as structured items (SDK input items, a Pi session file, a Claude resume file), not flattened text.

The loop and its tools

Each vendor's base prompt, agent loop, retries, streaming and tools stay. That's what makes each harness good, and why the design blindfolds memory, not the loop.

Guard rails

Where these systems go wrong, and the stop for each

Over-delegation

Anthropic saw 50+ subagents spawned for simple queries; multi-agent costs about 15× chat tokens. Rule: answer directly when it's QA or one quick lookup; spawn_bounds of 5 per wake-up; at most 4 running per main session (rakazo's MAX_PARALLEL_SUBAGENTS).

Conflicting workers

Cognition: parallel workers make incompatible implicit decisions. Rule: run in parallel only when there's no depends_on; dependent work is sequential and its context pack carries the earlier decisions.

Runaway chains

Depth 1: the main session spawns tasks; tasks can use their harness's own in-loop helpers but can't spawn task list tasks (rakazo: subagents "cannot nest further"; bot hops ≤ 6).

Runaway cost

Each task has a USD and time budget, enforced from the child's session_usage; hitting it ends the task as partial with whatever was found.

Retry loops

rakazo's failure brake (hint after 3 tool failures, stop at 8) inside tasks; the task list allows at most 2 automatic retries per task, then marks it failed with the error visible.

Injected content

Reports and artifacts are data. The assembler wraps them as untrusted, as rakazo does for bot messages and compaction summaries; only the main session's own rules are instructions.

In order, each shippable

Task list + spawn_task / finish_task on top of sys_session_create. Server-side wake on terminal child status. Works with today's main session context, so it's useful immediately.

Summary as a compaction item (the runner already loads from the latest one) plus the fresh_prompt flag, which calls close_session after every wake-up. The assembler returns prefix, middle and tail for the main session only.

core

Compaction cursor + maintenance agent: rakazo's compare-and-set cursor, run as an Omnigent scheduled task, also updating memory (Letta's sleep-time idea).

scale
4

Main session harness: openai-agents first (cheap rebuild, structured items); then a pi-sdk harness built on pi-agent-core, the way rakazo runs Pi.

quality
5

Evaluation: a fixed set of main sessions (question answering, one-task, fan-out, dependent chain, failing task, a main session with 200 wake-ups), checking cache hit rate, tokens per wake-up, answer quality and cost against a single-agent baseline.

Risks, stated plainly

What could make this worse than one agent

Report quality is the ceiling

The main session only knows what reports say. A lossy summary silently drops a crucial caveat. Mitigation: required confidence and open_question fields, artifacts by reference, and open_result for checking.

Latency of child sessions

A new task session can mean a runner launch; warm pools only save pod boot (designs/AGENT_SANDBOX_WARM_POOLS.md). Mitigation: keep one warm runner per active main session and send tasks to it.

Rebuild cost on stateful harnesses

Fresh-prompt wake-ups are cheap on SDK harnesses, expensive on a Claude Code process. Mitigation: choose the main session harness for rebuild cost; put the expensive engines in tasks.

Not every request should fan out

Cognition and "Building effective agents" both say most work should stay single-main sessioned. The main session's default is to answer directly; the eval in step 5 checks that it doesn't delegate by reflex.
