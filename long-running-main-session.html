Main session · months long

The session keeps everything. The prompt stays small.

A main session that lives for months will have thousands of messages. That's fine, because a session has two different things that people mix up: the record (Omnigent's database, which keeps every message) and the prompt (what the model sees on one wake-up). For the main session we don't let the harness manage context at all. The assembler builds a small prompt from the record every time.

What the main session actually carries

Flat. The summary absorbs old messages in batches, and recent messages are capped.

Illustrative numbers: ~350 tokens per message, a 200K-token model window, summary folds 50 messages at a time once 100 are unfolded (rakazo main's settings: history-compaction.ts, window 50, batch 50, summary ≤ 20,000 characters).

Who manages what

The harness never sees the record

One wake-up, step by step

Message 4,812 arrives

1

Your prompt is appended to the record as message 4,812 (Omnigent: POST /v1/sessions/{id}/events, stored as a conversation item).

2

The assembler builds the prompt: prefix (rules, core memory), the summary of messages 1–4,750, messages 4,751–4,812 as structured items, and a tail (open tasks, relevant past work, time, the trigger). About 10–20K tokens no matter how long the session is.

3

Omnigent starts a fresh harness with that prompt (the fresh-prompt flag). Nothing from earlier wake-ups is inside it, and no CLAUDE.md or AGENTS.md either.

4

The harness runs its loop (tool calls, maybe a helper or a task) and answers. Every item it produces is appended to the record, as today.

5

The harness is discarded. Nothing is kept in it for next time.

6

If 100+ messages are now outside the summary, a background job folds the oldest 50 into it and moves the cursor. It only moves if no other job moved it first, so two jobs can never fold the same messages twice.

And task sessions?

Short sessions can keep their own history

This is only a problem for the main session, because only it lives for months. A task session lives for minutes and ends with a report, so letting its harness keep its own history and compact it its own way is fine, and that's what native harnesses are good at. If a task somehow runs long, the harness's own compaction handles it, and the main session only ever sees the report.
