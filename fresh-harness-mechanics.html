How a harness ends up knowing only what we give it, and how it gets thrown away

No hand-waving: this is the path a message actually takes through the Omnigent runner into a harness today, the two existing mechanisms that make a fresh, assembler-fed harness possible, and exactly what each harness does when it starts fresh.

Correction to my earlier pages. I said the seam for history was history_to_input_items at runtime/workflow.py:2707. That's the server-side loop and the /compact command. The runner, which drives the harnesses, builds harness input elsewhere: _load_history_as_input and the in-memory cache _session_histories in runner/app.py. The design below uses the real path.

Two mechanisms that already exist

Bound the input, then discard the state

exists

1 · A compaction item bounds what's sent

The runner's loader only sends items from the latest compaction item onward, with that item's summary (or its compacted_messages) first. So the record can hold 5,000 messages while the harness input is "summary + the last few dozen". If the assembler's background summarizer writes our summary as an Omnigent compaction item, the existing loader does the rest.

# record, 4,812 items
[1 … 4,750]  # kept, never sent
compaction{summary: "…", compacted_messages: [...]}
[4,751 … 4,812]  # sent as is

2 · close_session throws the harness away

Every executor implements close_session(session_key) to "release per-session state" (inner/executor.py). Omnigent already uses it for exactly this purpose: on interrupt, Codex drops its session "so the next turn starts a fresh thread and replays full history" (codex_executor.py:4614). After it, the next run_turn takes the fresh path and uses the list it's given.

# openai_agents_sdk_executor.py:1203
async def close_session(self, key):
    self._session_states.pop(key, None)

# :1303 — next turn, fresh state

Put together: instructions come from the assembler through the per-wake-up hook (<deployment_context>, already live), history comes from the record starting at the assembler's latest summary, and no state survives between wake-ups because the runner closes the harness session after each one. The harness knows only what those two give it.

The proposal, in code terms

One wake-up of the main session

1

Your prompt is stored on the server and forwarded to the runner. The runner appends it to _session_histories[conv], which holds the last summary plus what came after.

2

The runner asks the server for instructions (POST /v1/sessions/{id}/deployment-context). The assembler returns the prefix (rules, memory) and the tail (open tasks, time, trigger).

3

The harness starts fresh because the previous wake-up ended with close_session, so run_turn uses the full list: summary, recent items, your prompt.

4

The harness runs its loop, with tools and possibly tasks, and its items are persisted to the record and appended to the cache, as today.

5

The turn ends and the runner calls close_session for this session (new: a per-session flag, e.g. the label omnigent.fresh_prompt=true). The Pi process exits, the Claude SDK client is dropped, the OpenAI Agents session state is popped.

6

When the unsummarized tail passes a threshold, the background summarizer writes a new compaction item to the record and tells the runner to drop its cache (_session_histories.pop(conv)), so the next load starts at the new summary.

This is why the design recommends openai-agents for the main session today, and a pi-sdk harness built on pi-agent-core (structured messages, as rakazo's pi-runtime.ts does) as the next step. Both can take a fresh start on every wake-up at almost no cost.
