# Recall is a bounded hint and a deep pull over one index in the Computer

A Conversation that runs for a year keeps its working list in the checkpoint and its history in the record, the journal and the person's files. The question was how the right part of that history reaches a turn: retrieved on every turn, or only when the model asks. Pushing retrieved text on every turn spends the attention budget and puts more untrusted text in front of every message; pulling only when asked depends on the model deciding to search, which is the "asked twice" failure. So Recall does both, split by cost. The full design is `docs/super-chat/recall.md`; this records the decision and the contracts the parts are built against.

- **One index, four sources.** The Computer's existing index (ADR 0014: SQLite FTS5 plus sqlite-vec, reciprocal rank fusion, embeddings through the model proxy) gains one source, `conversation`: one passage per completed turn of the person's own chats, written by the runner at turn end. The other sources already exist: `files` (the files area), `journal` (`memory/`), and `memory` (claims about the person, fetched from the engine and fused by rank). No new service, no new database, no open-source memory system (Letta, mem0, Zep and LangMem were weighed in the spec and refused: each owns a loop, a store or a framework we already have).
- **The pull is the deep path, on one surface.** A new `recall` tool takes up to three sub-queries, a set of sources, filters (`project`, `file`, `chat`, `since`, `until`) and a recency switch, and returns dated pointers with the id to read each one; `recall_get` reads any of them by id. They ship beside the old search tools, which leave the Muse's allow list one release later, after the evaluation has run on the new surface (spec section 9). The model writes its own sub-queries.
- **Work is joined to the objects it touched by code.** At each compaction, code takes the file, artifact, Project, Helper and chat references from the window's tool calls and writes them into each journal line; the index keeps them as metadata, so "what did we do on this file" is a filter, not a guess. An artifact version records the turn that produced it.
- **A Helper works where the Conversation points it.** `start_helper` takes a Project or a folder; the Helper's working directory is set before its Brief arrives.
- **The hint is the bounded path.** Every turn, when the owner's setting is on, a cheap planner call decides whether anything earlier is needed and writes up to three sub-queries; code derives them instead when the planner misses its cap. The result is at most eight dated lines and 300 tokens of identifiers, never bodies, fenced as data, built within a 1.2-second cap or not at all. The setting starts off; the paid "asked twice" evaluation decides whether it turns on by default.
- **Old is not wrong; old presented as current is.** The working list is the only source that says what is current. Every pointer carries its date, conversation turns lose rank with age (half every 90 days, never to zero, switchable off for questions about the past), versions of one topic collapse to the newest with the earlier dates listed, and an open entry untouched for 30 days shows `stale?`.
- **Nothing retrieved is evidence for a claim.** The conversation source indexes assistant text, so it is a lookup, never a belief; a hint quotes the person's words for a conversation hit, never the assistant's.

## Contracts

These are fixed so the parts can be built in parallel.

**C1. Conversation passages** (`omnigent/runner/knowledge/`): collection name `conversation`. One passage per completed turn of a main Conversation, Side chat or Fork (never a Helper, a steer or a system notice), text = the person's text, the assistant's final text and the turn's tool digests (`omnigent/context/tool_digest.py`), clipped to the index's passage limit. Metadata: `chat_id`, `turn_item_id` (the person's message item id), `date` (ISO, the turn's date), `origin` (`main` | `side` | `fork`), `project` (Project folder name or empty), `person_text` (the person's words, clipped, for hint snippets). Store functions: `index_turn(passage)` (idempotent on `turn_item_id`) and `delete_chats(chat_ids)`. Conversation passages never appear in file listings or file collections shown to the person.

**C2. Recall search** (`omnigent/runner/knowledge/recall.py`): `async recall_search(queries: list[str], *, sources: set[str], recency: bool = True, limit: int = 8, exclude_chat_after: dict[str, str] | None = None, project: str | None = None, file: str | None = None, chat: str | None = None, since: str | None = None, until: str | None = None) -> list[RecallHit]`; the filters match passage metadata (C1, C5) and dates. `queries` has one to three entries; `sources` is a subset of `{"files", "journal", "conversation", "memory"}`; `exclude_chat_after` maps a chat id to an item id after which its turns are left out (the current epoch). Each query runs BM25 and vectors; all lists are fused with the existing reciprocal rank fusion; the score is then multiplied by the recency factor (conversation only); near-duplicates collapse to the newest. `RecallHit` fields: `source`, `date`, `title`, `snippet`, `score`, `project`, `earlier` (list of older dates collapsed into it), and the read ids: `chat_id` + `turn_item_id` (conversation), `file_id` + `page` (files), `path` + `line` (journal), `claim_id` (memory). The `recall` tool and the hint both call this one function. Every hit has one stable read id with a type prefix (turn, journal line, file, claim) that `recall_get` accepts, alone or in a list.

**C3. Hint block** (spec 3.3): the exact header and footer lines of the spec, at most eight lines, at most 300 tokens, one optional `likely Project` line, prepended as a turn prefix block (`omnigent/superchat/prompt_prefix.py`), never stored. Per-owner preference key `recall_hint` (`on` | `off`, default `off`), stored where the owner's other preferences are.

**C4. Staleness**: `stale?` is rendered by the state file renderer for an open entry whose tag date is 30 or more days before the checkpoint date. The model asks about a stale entry only when the current message touches it, or once after an idle return, and never twice about the same entry.

**C5. References** (spec 8.2): `refs_from_items(items) -> dict[str, list[str]]` in `omnigent/context/refs.py`, pure, extracting from `function_call` items the keys `files` (workspace paths), `artifacts` (`id@version`), `project` (slug), `helpers` (run ids), `chats` (side chat ids); comma-separated values, no spaces, at most 12 per line. Written into the journal line's trailing comment after the chat id as `key:value,value` pairs, and into the compaction payload so a rebuild reproduces them. The indexer parses them from a journal line into passage metadata, and conversation passages carry the refs of their own turn. Artifact versions gain two nullable columns, `turn_item_id` and `chat_id`, written at save time.

**C6. Helper working directory** (spec 8.4): `start_helper` takes `project` (slug, resolved as `open_project` does) or `path` (workspace-relative); else the parent's current workspace; else the root. The runner sets it with `PUT /v1/sessions/{id}/workspace` after create and before the Brief. The path must resolve inside the workspace; a missing folder is an error back to the model.

## Consequences

- The Computer image and the engine need a rebuild; running Computers pick up the new runner on their next launch.
- Existing Conversations are backfilled into the `conversation` source once, in bounded steps, so recall covers their whole history.
- Deleting a Conversation removes its passages from the index as well as its `memory/` folder; a reset keeps them, like the journal.
- The planner adds one cheap model call per turn when the setting is on; its cost is recorded by the model proxy like any other call.
