Nova on Omnigent · engineering notes · branch omnigent-engine

One brain, any engine. How Nova builds what the model knows.

Omnigent runs the agent: Pi, Claude, Codex, OpenAI Agents or Hermes, on a runner in the Muse's computer or on your laptop. Nova is the layer that decides what that agent knows each turn and what it can do about it. This page traces a turn through both, with the real numbers from the code.

Baseline

How Omnigent already manages context

instructions

Layered instructions

The agent spec's instructions come first. Framework-owned instructions are appended after them in runtime/prompt.py (build_instructions). Harness adapters only transport the result.

delivery

Per-harness delivery

InstructionDelivery records how each harness receives instructions: composed-per-turn, composed-session-snapshot, agent-startup-additive, first-user-prefix. Per-turn harnesses rebuild the system prompt every turn, so injected context never piles up in history.

history

Layered compaction

Near the context window, runtime/compaction.py clears old tool bodies, then summarizes outside the recent window with an LLM call, then truncates as a last resort, from least lossy to most lossy.

The hook Nova uses: Omnigent can append a <deployment_context> block to the instructions on every turn. Upstream, that block came from an external HTTP provider called by the runner. Nova changed where it comes from and who is allowed to ask for it.

nova/context/composer.py

The composer: a byte budget with priorities

Each primitive exports context_section(request) → ContextSection | None, found by convention through _registry.section_providers(). The composer calls them concurrently (asyncio.gather(…, return_exceptions=True), so one failing primitive is logged and skipped), sorts by priority, caps each at its own size, and fits them into 48 KiB. Lower-priority sections are dropped whole, never cut mid-sentence.

static ~5K memory 32K goals 8K ep 3K 2K

Section caps add up to 51 KiB with the static text, so when every primitive is full the lowest-priority sections fall out first. In practice most turns use a few KiB.

Why instructions, not history

On composed-per-turn harnesses (Pi, Codex, OpenAI Agents) the block replaces last turn's copy, so a 40-turn chat carries one block, not 40. Static text comes first so the prefix stays cacheable, and the volatile sections come last.

Secrets never leak into context

Each section redacts request.secrets itself, and the composer redacts the whole result again. cap_utf8 trims on a line boundary and never splits a character.

nova/_shared

Privacy is a type, not a convention

fail-closed

Scope

scope_from_labels returns PRIVATE only for an explicit nova.scope=private. A missing or unknown label is PROJECT, and every private section returns None for it. The gateway labels every Nova session explicitly.

identity

One owner resolver

_shared.private_actor(conversation_id) is the only way a tool, the asks bridge or the episode observer learns whose data it is: session exists, label is private, and an explicit owner grant (owner_only=True). Six copies became one.

endpoints

Owner-only callbacks

/deployment-context and /builtin-tools/execute require LEVEL_OWNER. A collaborator with an edit grant gets 404, so a shared session can't read the owner's memory. A regression test locks this.

nova/episodes

Episodic memory: what Nova did, not just what it knows

Memory holds facts ("prefers short answers"). Episodes hold events: a dated record of a finished task, what was asked, what was found, and which tools did the work. This is what lets Nova say "last Tuesday we compared those two cards" without you repeating yourself.

Write path

1

Hook. In the relay loop (_relay_runner_stream_once), on response.completed the server fires on_turn_completed as a detached task held in _nova_episode_tasks. It is never awaited and catches everything, so it can't slow or break a reply.

2

Owner and scope through private_actor, off the event loop with asyncio.to_thread. Non-private sessions stop here.

3

Walk the turn. Up to 200 items newest-first back to the triggering user message: the last assistant message is the reply, and each function_call names a tool.

4

Only real work counts. Recorded only if a work tool ran (web search or fetch, browser, shell, file edits, terminal, research) and the reply isn't empty or NO_RESPONSE. Small talk leaves no episode.

5

Idempotent upsert on (workspace_id, session_id, turn_id), so a replayed completion never duplicates.

Read paths

A

Automatic. Every turn, the context section ranks the last 300 episodes against your message and injects the top 3 (3 KiB) as <past_episodes>.

B

On demand. When you say "last time" or "what did we find about…", the instructions steer the model to nova_recall_episodes(query, limit 1–10) over the last 1,000, falling back to the most recent with a note when nothing matches.

C

Feeds learning. The skills gate asks "has this person done similar work at least twice?" through the same ranker.

D

You're in control. GET /v1/nova/episodes and DELETE …/{id}, owner only.

Learning loops with guard rails

skills/gate.py

Skills are earned

An offer is refused unless the turn succeeded (not more failures than successes, and not the last 3 failed), the body is a procedure (a "When to use" line and a Steps heading with at least 3 steps), and there's evidence of reuse: at least 2 similar episodes (word overlap ≥ 0.5 over the last 200), or you asked or corrected Nova in this turn. An offer that resembles a saved skill (Jaccard ≥ 0.6) becomes an update offer. Each refusal names its rule so the model stops.

asks/bridge.py

Questions survive restarts

Omnigent keeps pending elicitations in memory. Nova mirrors each one on a private session into nova_asks (unique per elicitation id). Answering resolves the live elicitation if it still exists, and otherwise posts your answer into the session as a message, so the agent carries on.

engine switch

Same memory, any engine

engine.setHarness stores the choice on the Muse, and the gateway calls Omnigent's switch-agent between turns. The context block is composed by the server, so Pi, Claude, Codex and Hermes all see the same person.
